# R2-14 Owner 裁定（2026-07-29）：①级删除不写墓碑，改由界面说清后果

> 云端 AI 记录。触发者：PR #46 审查侧建议「待裁定 #3 应先于真机验证定口径」。

## 问题

`00-conventions §7.1` 的①级（从未上架）规定「物理删除，无墓碑」，验收①同样明写
「无墓碑」。但墓碑在 §7.1 里承担**两个**用途：

1. **保历史可读**——②级需要（实体没了，审计/订单行还要认得出它是什么）；
2. **挡回流**——「无墓碑硬删 = 垃圾循环回流，这是硬删除唯一的技术陷阱」。

用途 2 对①级**同样成立**，而 §7.1 把两个用途合在一处论证，落到①级时只保住了用途 1
的缺席理由（「本就没有历史可指向」），顺带把用途 2 也一起去掉了。

**为什么这条不是纸上谈兵**：本端点上线后第一个真实用途，大概率就是清理那批对拍残留
产品，而**那批全部落在①级**——删完之后只要有人再提交同一份 ASIN 清单，它们全部重新
入库，而代码、判据、CI 全绿，没有任何东西会报错。

## 开工前核过的一条事实（决定这条的分量）

`scrape.service.create_job` 全仓**只有一个调用方**（`scrape/router.py:76`，即 API 端点）：

```
grep -rn "create_job" backend/src/erp/ --include=*.py | grep -v "def create_job"
```

**没有任何 beat / 定时任务会自动重建采集作业。** 故①级的回流不是后台传送带，
而是「有人再提交一次同一份清单」才发生——仍会发生（清单多半躺在某个 Excel 里），
但不是自动的。

## 裁定

**Owner 2026-07-29：维持图纸，把话说清楚。**

- ①级仍不写墓碑，`§7.1` 与验收①**不改**；
- 前端二次确认弹窗**显式写出后果**：「若该产品从未上架，按规则不留墓碑——之后再提交
  同一个 ASIN 采集，它会重新入库。要让它彻底不再出现，请同时把该 ASIN 从采集清单里
  去掉。」
- 删除成功回执按级分别播报（①级明说「未留墓碑，重新采集仍会入库」）。

**取舍理由（Owner 采纳的推荐项）**：①级是**批量场景**（一次几百个）。给它留墓碑等于
一次性把几百个产品变成永久不可恢复，而**墓碑目前无法撤销**（见下「仍开着的一条」）——
误删的代价远大于回流的代价；且回流不是自动的，需要有人重提清单。

## 仍开着、本轮未动的一条

**墓碑不可撤销 → ②级误删不可恢复**（实体已物理消失，重采被墓碑挡）。是否开
「恢复采集」入口属范围决策，未自行动手，待 Owner/审计侧另行裁定。

> 上面那条裁定理由**依赖**这条仍然成立：若将来开了「撤销墓碑」入口，
> 「①级留墓碑风险太大」的论据就弱了一半，该条口径值得连带复议。

## 审查侧同时给出、云端侧已接的两条（不需要裁定）

1. **墓碑读取的 RLS 依赖写进 runbook**：`_deleted_refs` 受 RLS 管，空结果被当作
   「没有墓碑」放行——「真没有」与「有但看不见」是同一个绿。现在安全是因为采集走
   `system_tx`（带 `is_super`）；**谁把采集改成按团队会话跑，回流保护会零报错消失**。
   已落 `scrape/service.py` 函数头注 + `runbook.md`。
2. **墓碑多存 `product_id` / `master_sku` 的理由比云端侧原先写的更强**：
   `order_line.product_id`（`0025:164`）无外键，删产品后订单行要靠
   `deleted_product.product_id → master_sku` 才能反查「这行卖的是哪个产品」；
   而 `order_line` 属§7.1 的③级（绝不删）。**去掉那两列损失的不是审计页可读性，
   是③级数据的可追溯性。** 该理由已补进本轮批注，供审计侧确认时参考。
