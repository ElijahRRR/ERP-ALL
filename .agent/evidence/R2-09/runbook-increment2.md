# R2-09 增量2 运维手册：自动化档位面板

范围：`GET /api/v1/automation-policies`、`PUT /api/v1/automation-policies/{flow_code}`、
迁移 `0040_automation_policy_permissions.py`（新增权限码 `automation.read` / `automation.write`）、
前端页 `/automation`「自动化档位」。

本增量**只做面板**：面板可看可改，但除 `order_block` / `refund` / `cancel` 三条既有消费点外，
其余 flow 的档位改了**暂时不会有任何行为变化**（接线是增量3-5）。验收时不得把「改了 auto
但采集没自动跑」判为缺陷。

---

## ① 部署后怎么验（**必须用非超管账号**）

`backend/src/erp/core/authn.py:103-104`：**超管的 `permissions` 恒为空集**，
`CurrentUser.has()` 靠 `is_super` 无条件短路。所以超管永远能进面板，
**也就永远验不出授权到底发没发出去**。用超管验一遍全绿、普通用户全 403，是本项目已经
踩过的坑。

顺序：

1. 用一个**绑了「团队管理员」角色的普通账号**登录（不是超管）；
2. 左侧菜单应出现「自动化档位」（菜单由 `automation.read` 门控）；
3. 进页面应看到**恰好 10 行**——即便该团队一条 `automation_policy` 都没有
   （零行团队返回的是「注册表 ∪ 库中行」，无行的显示 `未配置（等同人工）`）；
4. 面板本身的四项（改档 / 闸类二次确认 / 三态渲染 / 无权限只读）逐项判据见 **§②**。

**前端是新页，必须重新构建部署**（`frontend` 的 `pnpm build` 产物 + 反代刷新），
浏览器再硬刷新一次（Ctrl+F5）。「菜单不出现」最省事的一次排查就是先确认这一步——
本项目已经踩过一次「后端上了、前端没重新部署，被当成权限问题查了半天」。

反向自证（可选，10 秒）：直接对闸类 flow 发 `mode=semi`，应得 **422 AUTOMATION_MODE_ILLEGAL**，
报文里列出 `manual/auto`。能拿到 422 说明服务层校验真的在跑（DB 的 `ck_automation_mode`
不区分 flow，挡不住这一条）。

## ② 面板四项逐项判据（改档 / 闸类二次确认 / 三态渲染 / 无权限只读）

**判据写法**：每项列出「怎么做」与「怎么算过」。**判据全中才算过**；任一不中就照
该项末尾的「不中说明什么」往下查，不要含糊放过——本面板控制的是全域流程开关，
「大概没问题」在这里的代价是某个团队的拦截静默失效。

### A. 改档（非闸类，最小闭环）

**做**：`pricing_watch`（盯价改价）行的「档位」点「半自动」。

**过**（五条全中）：
1. 右上角出现绿色提示「档位已保存」；
2. **不弹二次确认**——非闸类改档不该有确认框；
3. 状态列由灰「未配置（等同人工）」变为蓝「半自动」；
4. 「启用」开关变为蓝色「启用」（首次置档默认 enabled=true）；
5. 「最后修改」列出现「时间 · 用户 #<你自己的 user id>」。

**不中说明什么**：报 422 且报文列出合法档位 → 你点的档位对该 flow 非法（只会发生在闸类）；
报 403 → 该账号缺 `automation.write`；点了毫无反应 → 反代没把 `/api/v1` 转到后端，
或前端资源是旧的（回 §① 的构建部署那一步）。

### B. 闸类二次确认（两条路都必须弹）

**前置**：把 `order_block`（订单闸）切到「全自动」。这一步**不该弹**确认框——开闸不是危险动作；
切完状态列应显绿「全自动（拦截生效）」且红字消失。

**B1 档位路**：点该行「人工」。
**过**：① 弹出确认框，标题含「切回人工」；② 正文出现「只软标记不冻结」与「拦截将不生效」；
③ 主按钮是**红色**；④ 点「取消」后档位**仍是全自动**（不得静默改）；⑤ 再点一次「人工」并确认 →
状态列变「人工」且红字「拦截当前不生效」重新出现。

**B2 停用路**：把它切回「全自动」，然后关掉「启用」开关。
**过**：① 同样弹出红按钮确认框；② 正文含「停用后本流程退回 manual」+ 同一句警告；
③ 确认后状态列变橙「已停用（等同人工）」，红字「拦截当前不生效」**仍在**。

**反向判据（必须验）**：对 `pricing_watch`（非闸类）做同样两个动作，**两次都不得弹确认框**。
不验这一条就分不清「确认框真的按闸类挂」还是「所有操作都弹一下」——后者会被点成肌肉记忆，
等于没有确认。

**补充判据（审查 F2 加的，必验）**：直改库把 `order_block` 造成 `mode='semi'`（见 §C 的 SQL）
——此时档位**显示异常但订单闸真在拦截**。点「人工」**同样必须弹**红按钮确认框。
初版确认条件只认 `effective=auto`，恰好在这个唯一「显示异常但闸开着」的状态下不设防。

**不中说明什么**：确认框缺失 = 任何有写权限的人一次误点就能把该团队的**订单拦截**关掉
（合规闸未接线，见 §④），且事后只能靠审计日志倒查。这是本页唯一一处「必须挡在动作之前」的东西。

### C. 三态渲染（外加第四种：非法档位）

面板必须让 `unset` 与 `disabled` **一眼分得开**——两者生效结果都是 manual，但一个是从没配过、
一个是**被人关掉的**，后者才是要去问「谁关的、为什么」。读法详见 §⑤。

| 态 | 怎么造 | 判据 |
|---|---|---|
| `unset` | 新团队 / 没动过的行 | 灰 Tag「未配置（等同人工）」；档位选择器**无选中项**；开关关；最后修改「—」。**已接线的闸类**（`order_block`）额外显红字「拦截当前不生效」——新团队一进来就有**一条**红字，是真话不是 bug；`compliance_block` 因未接线只显示灰 Tag「未接线」，不显示红字 |
| `configured` | 做完 A 步 | 档位 Tag：人工=灰 / 半自动=蓝 / 全自动=绿；闸类跑 auto 时 Tag 文案是「全自动（拦截生效）」 |
| `disabled` | 做完 B2 步 | 橙 Tag「已停用（等同人工）」；**档位仍显示原来那档**（不清空）；开关关 |
| 非法档位 | 只能直改库造（见下） | 红 Tag「档位非法（semi），实际按「半自动」生效」+ 档位 Tag 带「（拦截生效）」后缀（semi 在订单闸上**真在拦截**）；**不显示**红字「拦截当前不生效」 |

造非法档位（排障演练用，验完改回去）：
```sql
UPDATE app.automation_policy SET mode='semi', enabled=true
WHERE team_id=<团队id> AND flow_code='order_block';
```
**判据的要害在最后一格**：闸类存着 `semi` 时面板显示的是「按 semi 原样生效」而不是「按人工」——
内核**只告警不改写**，擅自归 manual 会让该团队静默失去订单拦截。若面板显示成了「人工」，
说明前后端有一侧把非法档位改写了，那是**必须报的缺陷**。

### D. 无权限只读

**造**：给一个账号只挂 `automation.read`（或把团管副本的 `automation.write` 摘掉），
然后**重新登录**——权限在登录时装载进 token，不热更新。

**过**（四条全中）：① 菜单「自动化档位」仍在；② 10 行照常显示当前档位（**只读是禁用不是隐藏**，
看不见当前档位就没法判断要不要申请权限）；③ 工具条出现「只读（缺 automation.write）」标签；
④ 所有档位选择器与开关灰掉不可点。

**再摘掉 `automation.read` 并重新登录**：菜单「自动化档位」消失；手敲 `/automation` 进去
数据加载失败（后端 403）。

**不中说明什么**：控件可点 = 前端没按权限退化，误点会撞后端 403（不会写坏数据，但是坏体验）；
菜单还在但页面 403 = `/me` 返回的权限集是旧 token 的，重新登录即可。

> 沙箱曾以真实全栈（PG + uvicorn + vite + Chromium）跑过一轮 24 条断言（2026-07-28），
> 但**那一轮针对的是审查修复前的版本**——修复后（`wired`/`gate` 字段、确认条件扩到
> `semi`、「未接线」标签、GET 对无团队超管改 422）**未重跑全套**，且脚本未入仓。
> **故该轮不作为取证**（铁律：不可核的绿不算绿）；真机验证以本节人工步骤为准、逐条重验。

## ③ 既有团队用户看不到菜单——排查顺序（从最常见往下走）

**这个故障没有任何报错**，表现只是「菜单不出现」，所以必须按顺序查，不要跳。

1. **该用户绑角色了吗**
   ```sql
   SELECT r.id, r.name, r.team_id FROM app.user_role ur
   JOIN app.role r ON r.id = ur.role_id
   JOIN app.app_user u ON u.id = ur.user_id
   WHERE u.username = '<用户名>';
   ```
   空结果 = 用户一个角色都没绑。这是本项目历史上 `compliance_perms=0` 那次误判的真因，
   不是授权没发出去，是没人拿。→ 在「用户管理」页给他挂上「团队管理员」。

2. **该团队的「团队管理员」副本拿到两个码了吗**
   ```sql
   SELECT rp.permission_code FROM app.role_permission rp
   JOIN app.role r ON r.id = rp.role_id
   WHERE r.team_id = <团队id> AND r.name = '团队管理员'
     AND rp.permission_code LIKE 'automation.%';
   ```
   应返回 `automation.read` 与 `automation.write` 两行。
   **少于两行说明 0040 的回填没覆盖到这个团队**——注意模板角色（`team_id IS NULL`）的授权
   **不会**自动传播到既有团队副本，`identity/router.py` 的复制只在**建团队那一刻**发生一次。
   0040 是按角色名匹配、不带 `team_id` 谓词的，正是为了一并覆盖既有副本；这里查不到，
   要么团队的角色被改过名（匹配不上，静默什么都不发生），要么 0040 没跑（见第 3 步）。
   **反向须知**：同一个匹配规则意味着团队若**自建**过恰好也叫「团队管理员」的本地角色，
   会一并拿到这两个码——0031/0033/0035/0039 一脉相承的既有范式行为，不是 0040 独有。

3. **0040 到底跑没跑**
   ```sql
   SELECT version_num FROM alembic_version;          -- 表在 public，不在 app；应 >= 0040
   SELECT code FROM app.permission WHERE code LIKE 'automation.%';   -- 应有两行
   ```
   种子码都没有 = 迁移没跑到 head，先补跑迁移。

4. 前端拿到的权限集合以 `GET /api/v1/me` 为准（菜单按 `permission` 字段过滤）。
   后端查出来有、`/me` 里没有 → 该用户的 token 是授权之前签发的，**重新登录**即可
   （权限在登录时装载，不热更新）。

## ④ 闸类切档的影响面与回滚

闸类 flow 有两条：`order_block`（订单四检拦截）、`compliance_block`（合规黑名单拦截）。
**但两条的现状完全不同，不许并列理解**（审查 2026-07-28 F1）：

- **`order_block` 已接线**（`order/procurement.py` 真在读档位）——下述影响面**只对它成立**；
- **`compliance_block` 未接线**：全仓没有任何代码读它的档位，改成什么都**不改变任何行为**。
  面板对它显示灰 Tag「未接线（改档暂不生效）」，且**不渲染**「拦截生效/不生效」——
  对没接线的 flow 说这两句话都是假话。合规拦截目前**不由**这个开关控制。

对**已接线**的闸类而言 `manual` 不是「更保守」，是「更放松」：`auto`（含非法遗留的 `semi`）
才是「拦截 flagged 单」，`manual` 只软标记不冻结。所以下面三个动作**后果相同**——
该团队的订单拦截立刻不再生效：

- 把档位从 `auto` 切回 `manual`；
- 把该行 `enabled` 关掉（`resolve_mode` 视同 manual）；
- 该团队压根没配这条 flow（`unset` 也视同 manual）。

面板对这三态在「状态」列显红字「拦截当前不生效」（仅已接线的闸类）——
**新团队打开面板会看到一条红字（`order_block`），那是真话，不是 bug**。

**回滚方式：把档位改回 `auto` 即可，不要回滚迁移。** 求值语义是 `realtime`，
下一次订单决策即生效，无需重启服务、无需清缓存（档位**不进** ConfigService / Redis，
见 `core/automation.py` 模块头注）。

回滚迁移（`alembic downgrade 0039`）只会删掉两个权限码和它们的授权，**不影响任何档位数据**，
但会让所有非超管**失去面板入口**（菜单消失、API 403）。除非要整体撤掉本增量，否则不要做。

## ⑤ 三态在面板上怎么读

| 状态列显示 | 含义 | 实际按哪档跑 |
|---|---|---|
| `未配置（等同人工）` 灰 | 本团队库里**没有这一行**，从未配置过 | manual |
| `已停用（等同人工）` 橙 | 有行但 `enabled=false`——**是被人主动关掉的** | manual |
| 档位 Tag（人工/半自动/全自动） | 有行且启用 | 即所示档位 |
| 追加 `档位非法（xxx），实际按「yyy」生效` 红 | 库里存的档位不在该 flow 的合法集（例：`order_block` 上存着 `semi`） | 看红 Tag 里的 `yyy`：值解析得出（如 `semi`）就**原样生效、不归 manual**；值根本不是三档之一（绕过 `ck_automation_mode` 直改库塞进来的脏串）才回落人工 |

「未配置」与「已停用」在面板上**必须能分开看**——两者生效结果都是 manual，但
「配着但已停用」是最难发现的一类故障，压成一个字段之后就再也查不出是谁关的。

最后一行那种非法档位，DB 层是合法的（`ck_automation_mode` 只约束三档取值、不区分 flow），
只能靠面板暴露。**内核只告警不改写**：`order_block` 上的 `semi` 现行代码是拦截的，
擅自归 manual 会让该团队静默失去订单拦截。看到红字 = 该行需要人工改成合法档位。

服务端每命中一次这类边角会打 warn 日志，可按事件名捞：
`automation.policy_disabled_treated_as_manual` / `automation.unknown_mode_treated_as_manual` /
`automation.illegal_mode_for_flow`。

## ⑥ 已知边界（不是缺陷，验收时别当缺陷报）

- **超管不切团队时读写都拒**：GET 与 PUT 同口径返回 422 `AUTOMATION_TEAM_REQUIRED`，
  需带 `X-Act-Team` 头切到具体团队。初版 GET 曾按 team_id=NULL 静默查、返回一屏
  「全未配置」的假面板（它描述的不是任何团队，是「没有团队」），审查 F3 修掉。
- **PUT 不接受 `config` 字段**（返回 422 而不是静默忽略）：`automation_policy.config`
  目前全仓零消费点，开放写入只会造成「护栏已配」的错觉。GET 仍原样只读透传。
- **`snapshot` 型 flow 切档不影响在途请求**（`refund` / `cancel` / `purchase_execute`）：
  档位在请求创建时就固化进了该请求自己的 `mode_applied` 列。这是正确行为。
- **不分页、恒 10 行**：行数由 `AutomationFlow` 枚举定死，增删 flow 必须先改
  `specs/001-domain-model/09-platform.md` 图纸。
- **角色管理页上 `automation` 分组标题是英文**：该页按 `permission.module` 原样渲染，
  0040 之后仓内 11 个 module 全是裸英文，本增量不单独加中文映射。
- **未接线 flow 的改档只落库**：`wired=false` 的 flow（当前 7 条，含 `compliance_block`）
  改档不改变任何行为——面板有灰 Tag 标注。接线随增量3-5，接线 PR 必须同步更新
  `core/automation.py` 的 `WIRED_FLOWS`（T1 判据钉着，忘了会红）。
