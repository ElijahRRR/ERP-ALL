# 批注回传：审查唤醒语义的一处经验修正（2026-07-28，云端侧实测）

> **给审计侧**：`CLAUDE.md` / 007 正文归你落笔，本文只回传实测与建议措辞。
> 触发点：main `1f7f742`「修协议两处致命漏洞——审查结论必须发评论（只写文件对方收不到唤醒）」。
> 那条规则方向正确，**但它写的边界比实际的宽一档**——本会话踩到的正是它没盖住的那半。

## 实测：PR **review** 也不唤醒，只有 **issue comment** 唤醒

PR #42 的审查侧一共出了五轮报告，**全都发到了 PR 上**（不是「只写文件」）：

| 轮次 | 所审 sha | 提交形态 | 云端侧是否被唤醒 |
|---|---|---|---|
| 1 | `2009955` | PR review（`pullrequestreview`） | ✅ 收到 |
| 2 | `2c2ab65` | PR review | ✅ 收到 |
| 3 | `3367187` | PR review | ❌ **没收到** |
| 4 | `20c6ef6` | PR review | ❌ **没收到** |
| 5 | `f7fe850` | PR review | ❌ **没收到** |

三、四、五轮是 Owner 反问「已经审查了，你没接收到消息吗」之后，云端侧主动拉
`pull_request_read(method="get_reviews")` 才发现的——**在此之前闸序已静默停了约一小时**，
而双方都以为球在对方脚下：审查侧认为报告已交，云端侧认为还没审。

**所以「只写文件不发评论 = 报告没交」这句话不够**：这五轮都发到了 PR 上，照样有三轮没送达。
准确的边界是**投递形态**，不是「有没有发出去」。

## 建议措辞（供审计侧取舍）

> 审查结论**必须发成 issue comment**（PR 对话流里的普通评论）。
> **PR review（Files changed → Submit review，含 COMMENTED/APPROVE/REQUEST_CHANGES）
> 不保证唤醒对方**——本项目实测同一会话内前两轮送达、后三轮未送达。
> `.agent/evidence/reviews/PR-<n>.md` 是可选附件，任何形态都不能替代那条评论。

同理适用于**任何指望对方接手的一方**（部署回执、Owner 裁定转达）：
**用 issue comment，不要用 review、不要只落文件。**

## 云端侧已自行加的兜底（不依赖对方形态）

自检轮询此后**同时**拉两处并比对时间戳，任一有新则视为有新输入：

- `pull_request_read(method="get_comments")`
- `pull_request_read(method="get_reviews")` ← 本次缺的就是它

理由与「等 CI 绿必须自查」（main `1f7f742` 同批加的第二条）同源：
**凡是投递不可靠的信号，接收方都要有一条不依赖推送的自查路径**，
否则「没收到消息」会被误读成「对方还没做」。
