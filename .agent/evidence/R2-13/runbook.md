## 一、开一个买家账号（从零到能拉单）

四步，缺任何一步插件都拉不到单：

1. **建账号**（「买家账号池」→ 新建）。三个必填项：
   - **账号名**：语义 = **对应哪一个指纹浏览器**。运营靠它把系统里的号与桌面上开着的
     窗口对上，随手写「号1」将来一定认不出来。
   - **站点**：`amazon_com` / `amazon_ca` / `amazon_co_jp`。派单按**收货国**匹配站点
     （US→com、CA→ca、JP→co.jp），对不上的单**不派**（不猜）。
   - **customerId**：**不是系统生成，也不是亚马逊页面上直接能看到的东西**。取法：
     在指纹浏览器里打开该买家账号的亚马逊页面 → 点插件面板「提取 customerId」→
     复制粘贴（形如 `A1NS3HIW4IC6P7`）。
2. **签发插件实例**（该行「插件实例」→ 签发新实例）。
   **令牌明文只显示这一次**，关掉窗口就再也取不到（服务端只存 sha256）。遗失只能吊销后重签。
3. **把两个请求头配进插件**：
   ```
   X-Plugin-Instance: <实例 id>
   X-Plugin-Token:    <签发时那串明文>
   ```
   端点前缀 `/api/v1/purchase-plugin/`（六个端点，末段保留厂商方法名）。
4. **确认账号状态是「启用」**，且当日未超「单日上限」。

### 一个实例 = 一台装了插件的浏览器

令牌是**实例专属**的，**禁止多机共用一把**。多开一台就多签一个实例：
这样吊销、掉线判断、版本对照都能落到具体一台机器上；共用一把则出问题时无从收敛。

## 二、执行档三挡（**唯一决定会不会花钱的开关**）

档位挂在**实例**上（不是账号），在实例抽屉里改。

| 档 | 插件行为 | 服务端落什么 |
|---|---|---|
| `dry_run` | 不进结账页 | **一个金额列都不写**，状态不动 |
| `stop_before_payment`（**新实例默认**） | 走到付款前停下并回报 | 写金额/卡尾号/预计送达；**不写渠道单号、不改状态**（停在 `assigned`） |
| `live` | 完整下单 | 全量落库，状态推到 `purchased`，渠道订单推 `purchasing` |

- **新签发的实例默认 `stop_before_payment`——不会花钱。** 升到 `live` 是一次显式操作，
  前端有二次确认、服务端写 audit。
- 插件回报时会**回声**自己跑的档；与实例当前档不符 → `409 PLUGIN_EXEC_MODE_MISMATCH`，
  回填被拒。**这条报错的正确处置不是改档重试**：先看插件日志确认那单到底有没有真下出去，
  下出去了就人工回填，没下出去再把插件升到与实例一致的版本/档位。
- 演练档却带回了渠道单号 = 「说好不花钱但花了」，服务端按**已下单**入账并升 critical 告警。
  见到这条告警要立刻停掉那台插件查原因。

## 三、怎么看「插件还活着吗」

- 列表页**最近上线**列：由插件的两个拉取端点写（`last_seen_at`）。
  **超 24 小时标灰并写「疑似掉线」**；从未上线也算掉线。
- **在用实例数为 0** 的账号：显示「0（无实例，拉不了单）」——建了账号没签实例是最常见的
  「怎么一直不拍单」的原因。
- 买家账号本身**没有心跳**。所以「今天没单」有三种可能，按这个顺序排查：
  ① 账号不是「启用」；② 无在用实例 / 实例已吊销；③ 当日已到上限；
  ④ 候选池里就没有符合站点的待采购单。

## 四、账号被风控 / 要停一停时

改**状态**，不要删（本期没有删除入口，删除分支挂在 14b 之后另补）：

| 状态 | 用在什么时候 |
|---|---|
| `active` 启用 | 正常派单 |
| `paused` 暂停派单 | 临时停一停（换 IP、人工核查、白天限流） |
| `blocked` 已风控 | 亚马逊侧已经出问题（要求验证、下单被拒） |
| `retired` 已退役 | 这个号不再用了 |

**三种非 active 的共同后果只有一个：不再派新任务。**
**但已经派出去的单，其回填 / 异常 / 物流三条写路径照常收**——这是刻意的：
钱可能已经花出去了，账号一停就连回填也拒收，等于**花了钱系统不知道**。
所以停号之后仍要盯几天那批在途单的回填。

要彻底切断某台机器：**吊销那个实例**（令牌立即对全部端点 401），而不是只停账号。

## 五、单日上限（`daily_cap`）

- 落点**只有** `buyer_account.daily_cap` 这一列。日限没有第二处配置，
  `automation_policy` 的 flow config 里**不得**出现同名键（Owner 2026-07-30 裁定）。
- 口径 = **当日已派发且未取消的单数**，不是拍成的单数。
  否则一个账号可以被派 100 单再一口气拍完，帽子形同虚设。
- **留空 = 不限**。页面上把上限清空并保存即改成不限。
- **续拉不消耗额度**：插件重启后重新拉，仍能看到自己已被派的单，不会因为额度用完就丢单。
- **日界时区**在配置中心 `procurement.plugin_dispatch.day_boundary_tz`，**默认 `UTC`**
  （`pull_batch_max` 默认 20、硬上限 100 同键）。时区名配错只会降级回 UTC 并告警，
  不会把拉取链打成 500。**这个默认值是待 Owner 裁定的口径**（见 §八）。

## 六、异常与告警：看到了怎么办

### 6.1 先分清「异常」和「问题分类」——**这条搞反会导致重复下单**

- **单据状态 = `exception`**：任务失败、**没有产生采购**（插件回报端点 3/4）。
- **`exception_kind`（问题分类）非空但状态仍是 `purchased`**：**钱已经花了**，
  只是回填后核对不通过（ASIN 不符 / 邮编不符 / 金额三项加总不平 / 单号冲突）。
  订单页面板会在这种情况下额外提示「已经拍出去了，请勿重拍」。

### 6.2 分类表

| 分类 | 含义 | 典型处置 |
|---|---|---|
| `address` | 地址保存超时 / 地址不完整 / 州识别不出 | 核对收货地址，必要时人工下单 |
| `stock` | 无库存 / 售罄 / 加不进购物车 | 换货源或转人工 |
| `product` | **非 FBA / 捆绑商品 / 改不了数量** | 需要换 ASIN——这类会升 critical |
| `delivery` | 预计送达超期或解析不出 | 看是否接受，或换货源 |
| `checkout` | 验证失败 / 下单验证超时 / **回传订单失败** | ⚠️ 「回传订单失败」意味着**单可能已经下出去了**，先去亚马逊后台查，不要直接重拍 |
| `price_guard` | 价格护栏拦截 | **本轮无写入路径**（属 13c） |
| `channel_cancelled` | 渠道回报已取消/退款（状态 91） | **已拍单之后**发生，要发起退款/换购 |
| `order_not_found` | 渠道回报查无此单（状态 92） | 同上，人工核 |
| `other` | 归类不到上面任何一条 | 看 `exception_reason` 原文 |

### 6.3 告警去重键（查通知中心时按这个搜）

| 键 | 触发点 |
|---|---|
| `plugin.site.<poId>` | 收货国缺失或不在站点映射表里 → 该单不派 |
| `plugin.no_asin.<poId>` | 订单行没挂上 amazon 货源 ASIN → 该单不派 |
| `plugin.dup_ref.<poId>` | **同一任务回填了两个不同的渠道单号**（重复下单的形状，critical） |
| `plugin.backfill_check.<poId>.<kind>` | 回填后核对不通过（ASIN/邮编/金额） |
| `plugin.task_failed.<poId>.<kind>` | 插件回报任务失败 |
| `plugin.channel_status.<poId>.<kind>` | 渠道回报 91/92 |
| `plugin.tracking_json.<poId>` | 物流事件数组解析失败（**运单号仍照常入库**） |

## 七、常见错误码

| 码 | HTTP | 含义与处置 |
|---|---|---|
| `PLUGIN_AUTH` | 401 | 认证失败。**故意不区分**「实例不存在 / 令牌错 / 已吊销 / 没带头」——四种同码同状态。处置：确认两个头都带了、实例没被吊销；仍不通就重签一把 |
| `PLUGIN_TASK_NOT_OWNED` | 403 | 拿了**别的团队**的任务 id 来回填。不存在的 id 与他团队的 id **同码同状态**（不泄露存在性）。⚠️ 同团队、派给另一个买家账号的单**不会**报这个码——那是有意放行的（换号后旧单必须报得回来） |
| `PLUGIN_EXEC_MODE_MISMATCH` | 409 | 见 §二 |
| `PROCUREMENT_PLUGIN_DISPATCHED` | 409 | 在订单页对**已派给买家账号**的单点了「分配采购方」。这是双保险的应用层那一半：同一单不许既派机器人又派人。要转人工得先把这张单处置掉（异常/取消） |
| `BUYER_ACCOUNT_DUPLICATE` | 409 | 建号撞唯一键。报文里 `detail.field` 指明撞的是 `external_customer_id`（同一个亚马逊号已建过，去改那条）还是 `label`（换个名字） |
| `BUYER_ACCOUNT_REJECTED_IMMUTABLE` | 409 | **结果态为驳回**的请求想挪动 `external_customer_id`——包括改一条已驳回行的 id，也包括把「驳回 + 改 id」合并成同一次 PATCH（整个请求原子拒绝，驳回也不会生效）。驳回是终态，靠这一行永久占住那个 customerId 才能挡住「同一个伪造 id 再灌」；改掉它等于撤销驳回。要给新 customerId 建号请另建一条；「整表单回填 + 驳回」（id 原样带回）不受影响照常 200 |
| `BUYER_ACCOUNT_STATUS_NOT_CREATABLE` | 422 | 建号时把 `status` 直接填成了 `pending_claim` 或 `rejected`。这两个是**系统态**：前者由插件首见自动登记产生，后者只能从待认领行驳回而来（直接建出来是一条改不动也删不掉的死行）。建号只收 active/paused/blocked/retired |
| `PLUGIN_INSTANCE_REVOKED` | 409 | 已吊销的实例不能改档，请重新签发 |
| `TEAM_REQUIRED` | 409 | 签发插件令牌时当前主体没有团队（超管未切换到具体团队）。令牌绑定的就是「团队 T 的一台授权浏览器」，没有团队的令牌解析不出任何任务 |

### 没有 `PLUGIN_CUSTOMER_MISMATCH` 这个码了

身份模型更正（Owner 2026-07-30，图纸 `07:288-340`）之后**它连同整条路径一起删除**：
`customerId` 是**路由参数**不是鉴权凭据，团队内换号是正常运营动作，不是越权。

**新模型下同一现场的表征**（拿这一条排障，别再去找那个 403）：

> **登了一个还没认领的号 → 拉取返回 `200` + 空 `data` 数组 → 买家账号池里冒出一条
> 「待认领」行 → 同时来一条通知「发现未认领的买家账号（插件首次上报）」。**

处置：到买家账号池找那条待认领行，**补齐账号名与站点后认领**（转 `active`），该浏览器
下一次拉取就正常收单；若那个号不是我们的，**驳回**（终态，此后不再自动登记）。

三条排障提示：

- **不是认证问题，别去重签令牌**——令牌若无效会是 `401 PLUGIN_AUTH`，而这里是 200。
- **「一直空数组、池子里也没有新行」另有两种可能**：①那个号已被驳回（查
  `status=rejected`，列表默认折叠，要勾「显示已驳回」）；②本团队待认领行**已达上限**，
  新号被拒绝登记——那时会有一条 critical 通知「待认领买家账号已达上限」，正文里带撞闸
  实例号与本团队已驳回行数。
- **`customerId` 对不对，看实例列表**：`last_seen_customer_id` 及其 JOIN 出来的账号名/
  账号状态就是「这台机器最近一次登的是哪个号、认领了没有」（观察值，不参与鉴权）。

## 八、本轮**明确没有**的东西（别去找，也别顺手补）

1. **cookie 整条链**：没有 `updateBuyerCookie` 端点、没有 `buyer_session` 表，
   任何 cookie jar 不落库（Owner 2026-07-30 二次裁定；有一条不变量测试盯着）。
2. **护栏三键**（`amount_ceiling` / `price_delta_pct` / `delivery_days_limit`）与
   `purchase_execute` 三档接线：属 13c，本轮不实现、不留假配置键。
   `pending_review` 状态本轮**只扩了词表，零转入路径**。
3. **异常单没有自动出边**（FX-0730B）：本轮新增了多个 `status='exception'` 的写入点，
   但全系统离开 `exception` 的路径目前只有「删除采购方」的副作用，而插件单没有采购方
   ⇒ **异常单目前需要人工在 DB 层处理**。「重置回待派发」端点设计已完备但**未获裁定**，
   本轮未实现。
4. **日本站不做**：`amazon_co_jp` 取值、`receivingDistrict` 字段、JP 地址分支全部**保留**，
   但本轮不投入使用（不做 ≠ 删掉）。
5. **插件侧代码不在本仓**：fork 与改造（双头部注入、路径改一组、删 cookie 权限、
   补 execMode 三档）落在外部仓 `ElijahRRR/AMZ-Purchase-Assistant`，本轮 ERP 侧只交付
   服务端契约 + 认证 + 表。**服务端就绪不等于插件已改好。**
