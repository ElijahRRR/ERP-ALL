# 单人模式流程规约（D-Q74，2026-07-30）

> **给谁读**：所有参与本仓的 AI（开发/审查/部署/规划）与 Owner。本文是流程唯一事实源，
> 与 `CLAUDE.md` 冲突时**以本文为准**（落地清单第 1 条会把 CLAUDE.md 改到一致）。
>
> **为什么有本文**：D-Q73 把系统收敛为单人自用后，Owner 指出臃肿感的另一半来自流程
> ——每个增量一律四闸+十几条判据+多轮审查，是给多人生产系统设计的重量。实证：
> PR #49（一张删除功能单）审查跑了九轮，末几轮只在打磨文案；一张 docs PR 也走全套。
> 单人系统的流程原则：**仪式的重量与出错的代价成正比，而不是与改动的大小成正比。**

---

## 一、改动分级（核心表，先查这张再动手）

| 级 | 什么改动 | 要求 | 不要求 |
|---|---|---|---|
| **L0 轻装** | docs / specs / `.agent` 台账回写 / 注释 / 前端文案与导航 / 纯加测试 / 只读页面 | CI 绿 | 审查、真机、立单、台账回写 |
| **L1 标准** | 其余一切代码改动（后端逻辑、前端功能、无数据变更的迁移） | CI 绿 + 审查**一轮** | 真机验证（随下次部署批量点验） |
| **L2 全闸** | ①**渠道写路径**（feed 提交/改价/下架/订单发货取消——任何写到 Walmart 的）②**花钱**（采购执行、LLM 预算）③**删数据**（硬删除、含数据变更的迁移）④**安全边界**（免登录开关、token、对外暴露） | 现行四闸全套：CI 绿 → 审查 → 部署机真机 → Owner 授权 | —— |

判级拿不准时：**按高一级处理**，但在 PR 里写一句"按 LX 处理，因为——"，让 Owner 有机会降级。

## 二、审查纪律（对审查 AI）

1. **L0 不进审查队列**——看到 L0 PR 不审，Owner CI 绿即可合并。
2. **轮次上限 = 2**：首轮全量给出；第二轮只验证首轮修复。两轮后仍有 blocker → 停下推给
   Owner 裁决，**不许第三轮**。
3. **意见分两类，打磨类不强制修**：
   - **缺陷**（会造成错误行为/数据损失/契约破坏）：必须修，阻塞合并；
   - **打磨**（文案、命名、风格、"更好的写法"）：一次性列出，开发侧**自主取舍**，
     不修不阻塞、不追问、不复审。
   PR #49 九轮的病根就是打磨类被当缺陷追着改——此后再发生即违规。
4. 审查评论开头标 `[缺陷]` 或 `[打磨]`，让 Owner 一眼看清什么在阻塞。

## 三、工单与判据（对开发 AI 与规划 AI）

1. **半天以内的活免立单**：直接开 PR，正文三行内说清"改了什么、为什么、判级"。
   台账不回写。
2. **立单门槛**：预计超过半天、或 L2、或跨多个模块的改动才立单。
3. **判据上限**：L1 单 ≤ 5 条，L2 单 ≤ 8 条。只写**不做会造成实际损失**的证伪判据；
   "证明设计正确"的自证判据不写（历史教训：R2-13 判据③第三条就是自证判据，已删）。
4. **台账回写只在两处**：立过单的收账时一次、状态变更（accepted/deferred）时一次。
   过程进展不回写台账，写 PR 里。
5. **新判据一律不写**：越权/权限点/角色/多团队（D-Q73 已裁）。

## 四、真机验证批次化（对部署 AI）

1. **L2 单独验**：每张 L2 在合并前真机走完（现行做法不变）。
2. **L1 不单独验**：随下一次例行部署**批量点验**——部署后跑一遍冒烟清单
   （首页/产品/订单/定时任务面板各开一次 + healthz），有异常再回溯到单。
3. **合并后必须部署**：任何合并后 24h 内部署机拉一次 main（R2-14 的教训：验收通过
   但线上跑旧代码，Owner 看不到功能）。部署回执一行即可。

## 五、不变的部分（这些不是仪式，是保险丝）

以下各条**不因流程裁剪而放宽**，任何 AI 不得以"单人模式"为由绕过：

1. **合并授权永远在 Owner 手里**——开发与审查同为 Claude，两边一致也可能一起错。
2. **升级清单原样保留**（CLAUDE.md）：花钱 / 删数据或不可逆 / 范围增减 / 业务口径 /
   与宪法冲突 / 安全边界放宽 / 对外暴露 / 需要凭证——**停下来问，不自行拍板**。
3. **PR 正文不变量规则**保留（已有 5 次正文失实的实证，靠自律修不好）：不写会漂的
   计数，要写就写可复算的不变量。L0/L1 正文短即可，但不许失实。
4. **CI 机器门禁全部保留**（台账结构、finding 上限、中文禁则、契约测试）——它们零人力
   成本，裁掉无收益。
5. **状态在仓库不在会话**：台账与 specs 仍是唯一事实源。
6. **渠道写路径的 dry-run 证据**（D-Q37）保留——那是防真实店铺事故的，与流程无关。

   dry-run 证据那半句**保留在渠道写路径上**（见 §五.6）。
2. **通知开发 AI 与审查 AI**：各自 PR/评论流里贴一次本文链接与分级表；审查 AI 确认
   「L0 不审、两轮上限、缺陷/打磨分标」三条。
3. **通知部署 AI**：批次化点验规则（§四）+ 合并后 24h 部署纪律。
4. **回写台账**：R2-18 状态置 done，updates 记落地时间与改动的 CLAUDE.md 行号区间。
5. **一周后自查一次**（用 send_later 或例行唤醒）：抽最近 5 张 PR，检查分级是否被用、
   审查是否超轮、L0 是否被误审——有偏差在台账 R2-18 追加一条 progress 记录并纠正。

## 七、预期效果（Owner 用来验收本规约本身）

- docs/文案/小修类改动：从"立单+四闸+回写"降为**开 PR → CI 绿 → 合并**，当天可完；
- 普通功能增量：审查最多两轮，不再有真机排队；
- 花钱/删数据/渠道写/安全边界：**和以前一样严**，一步不少。
