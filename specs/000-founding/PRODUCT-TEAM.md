  目标是从零正式开发"完整满足现有需求 + 可持续扩展"的 ERP 产品。

## 0. 项目负责人的开场判断（一条必须先说的经验教训）

从零开发最大的风险不是写代码，是**需求挖掘不全**——你上次迁出重构失败，根因就是新系统
追不上散落在 13 个工具、几千行注释和你脑子里的业务规则（UPC 复用策略、907xx 错误处置、
定价倍率、每店 360 秒节奏、风控四检……）。所以本计划的铁律：

> **代码可以从零，需求必须考古，验收必须对拍。**
> 旧系统在新系统逐模块达到对拍一致之前不许停机——它就是活的需求文档和验收基准。

## 1. 职能团队编成（9 顶帽子 + Owner）

### PL 项目负责人（我）
- 整体计划与节奏、跨职能仲裁、风险管理、范围控制（砍需求的人）。
- 对你的接口只有三类：决策请示、迭代演示、风险上报。

### PM 产品经理
- **最重的前期角色**。负责"考古"：把 13 个零散工具 + erp-core 草稿逐个翻译成
  业务规则清单 → PRD → user story（含验收标准）。
- 维护唯一 backlog 与优先级；每条需求写清楚"为什么"（业务价值）与"怎么算做完"（可执行验收）。
- 产出物：《业务规则总账》（本产品最有价值的文档）、PRD v1、迭代验收单。

### AR 资深全栈架构师
- 领域模型（master_sku 标准、channel adapter 抽象、listing 状态机）、数据库 schema、
  API 契约（OpenAPI 先行）、技术选型与非功能需求（性能/扩展性/部署形态）。
- 每个重大决定写 ADR（架构决策记录）；把关所有 breaking change 与 migration。
- 兼任 DevOps 帽子：CI/CD、监控告警、备份、发布流程（本项目规模不值得单设）。

### UX UI/UX 设计师
- 先做**信息架构**：运营者一天的真实工作流（选品→审核→上架→盯错→订单→售后→复盘）
  决定导航与页面结构——这恰是现有前端缺的环节（mock-first 拼页面、五页零 fetch 的病根）。
- 低保真原型验证工作流 → 设计系统（组件/状态/空态/错误态规范）→ 高保真。
- 纪律：任何页面先有原型和数据契约，再写代码；禁止 mock-first。

### BE1 后端工程师·领域服务
- 领域逻辑实现：catalog/listing 生命周期/orders/aftersales/audit/pricing 服务层与任务编排。
- 纪律：服务层与 API 层分离（吸取 v5_data.py 2400 行裸 SQL 的教训），API 只做编排与鉴权。

### BE2 后端工程师·渠道集成
- Walmart API 客户端、限流（GCRA + 响应头自适应）、feed 语义、代理路由、采集器。
- **唯一允许写"打到真实渠道"代码的人**；一切变更附 dry-run 证据；官方文档核对是其日常。
- 现有草稿中采集器（AIMD）与 walmart_client 是工程质量最高的部分，允许"考古后移植"而非重写。

### FE 前端工程师
- 按设计系统 + OpenAPI 契约实现；契约由 AR 冻结版本，FE 与 BE 并行开发、契约测试对齐。
- 技术栈建议：从"无构建 React UMD + Babel standalone"升级为正规 Vite + React + TS 工程
  （现有形态是原型工具，撑不起长期产品）。

### QA 测试工程师
- 测试策略分四层：单测（服务层）、契约测试（前后端接口）、dry-run E2E（全链路不落真单）、
  **影子对拍**（新旧系统同输入比输出，是"从零重写不翻车"的核心保障）。
- 维护 CI 门禁与接线审计回归工具（端点↔调用方/ 任务↔派发 / 表↔读写，防"半接线"复发）。
- 有权 block 合并。

### SEC 安全研究员（阶段性介入，非全程）
- 介入点 1（设计期）：凭证管理方案（加密存储/轮换）、认证授权模型（同事多用户）、
  店铺关联风险面（代理绑定不可绕过——walmart_client 强制层）。
- 介入点 2（对外暴露前）：依赖审计、渗透检查（吸取 erp_listing_server 公网裸奔 + 凭证入库教训）。
- 介入点 3（例行）：季度性凭证轮换与泄露扫描。

### Owner（你）——唯一领域专家 + 客户
- 需求澄清（PM 考古时的口述历史来源）、每迭代验收、优先级最终裁量；
- 生产钥匙：凭证、live 放量审批、真实上架抽检。
- **你不写代码、不改库**——你的时间全部花在"说清楚业务"和"验收"上，性价比最高。

> 执行说明：以上是职能而非人头。AI 团队里一个 agent 可以戴多顶帽子，但**同一交付物的
> 作者与验收者必须是不同角色**（如 BE 写的代码 QA 验，PM 写的验收标准 Owner 签）。

## 2. 开发任务规划（四个阶段，每两周一个可演示增量）

### R0 需求与设计（2-3 周｜PM+AR+UX 主导）
| 产出 | 负责 |
|---|---|
| 《业务规则总账》：13 工具 + erp-core 逐个考古，规则逐条编号（可追溯到源码位置） | PM |
| PRD v1 + MVP 边界（哪些功能进第一版，哪些明确不做） | PM |
| 领域模型 + 数据字典（含 master_sku 标准落锤）+ OpenAPI 契约 v1 | AR |
| 信息架构 + 核心工作流低保真原型（你过目确认） | UX |
| 凭证与权限方案 | SEC |
| 测试策略与影子对拍方案 | QA |
- **验收门**：你签字 PRD 与原型后才动第一行产品代码。

### R1 行走骨架（3-4 周｜全员）
- 一条**最小闭环**端到端贯通：1 家店、1 个 ASIN——采集→审核→上架(dry-run)→轮询→状态回写→前端看板可见，含失败路径。
- 骨架从第一天携带全部地基：认证、CI、migration、结构化日志、告警、测试四层骨架。
- **宁可窄，不可断**——每个环节都真实接线，杜绝"先做端点后补对接"。
- 验收门：给你现场演示全链路（含制造一次失败看告警与错误处置）。

### R2 领域纵深（8-12 周｜两周一迭代，按业务价值排序）
| 迭代主题（示意顺序） | 验收标准 |
|---|---|
| 上架生命周期完整态机（含 UPC 池、错误分类处置、风控门） | 与旧 auto_listing 影子对拍 7 天一致 |
| 定价/库存维护 + 配额调度 | 对拍 + 配额门控可证明生效 |
| 订单 + 采购方 + 四检审核 | 对拍旧订单审核模块 |
| 售后 returns + 联动策略 | 新增能力（旧系统只有同步） |
| 报表/KPI/日报 + 通知 | 数字与旧日报一致 |
| 跟卖通道 + 批量下架 | 对拍 |
- 每迭代 UX 先行一个迭代出高保真；FE/BE 契约并行；QA 影子对拍收尾。
- 数据迁移贯穿：每个模块切流前完成对应历史数据 ETL + 对账（数据工程帽子由 BE1/AR 分担）。

### R3 切流与退役（2-3 周/批）
- 按店铺分批切流（建议先 5 家试点店全链路跑新系统两周）→ 全量 → 旧工具逐个退役登记。
- SEC 在对外暴露（同事访问）前做一次完整检查。

### R4 扩展性验证（按需）
- 第二渠道 adapter 试点、多用户权限、上服务器部署——验证"可不断扩展"的承诺兑现。

## 3. 编排机制（项目负责人怎么管）

1. **单一 backlog**：所有工作以工单存在（沿用 .agent/review_list 机制升级为产品 backlog），
   没有工单的改动不合并。
2. **任务卡**：目标 + 验收命令 + 文件边界 + 禁区 + 证据要求；作者与验收者分离。
3. **节奏**：两周迭代；迭代末=可部署 + 给你演示；WIP 上限 3。
4. **质量门禁**：CI（lint+单测+契约测试）→ dry-run 证据 → 影子对拍报告 → 接线审计回归。
5. **文档纪律**：spec/ADR 先行；《业务规则总账》是活文档，考古新发现随时补录。
6. **决策日志**：所有你拍板的决定（D 系列）记录在案，防止后续 agent 会话反复重问。

## 4. 与既有 PLAN.md 的关系（D0 决策点）

- PLAN.md（演进式绞杀）与本文（从零重写）共享同一批资产：调研、接线审计、业务规则考古。
- 差异只在 R2 各模块的"移植 vs 重写"比例。**建议**：默认重写（换干净地基），
  但采集器、walmart_client/限流、审核 L0-L4 这三块草稿中质量最高的允许考古移植。
- **D0（新增决策点，请拍板）**：正式确认走"从零产品化"路线（本文）替代"原地演进"（PLAN.md Phase 2B 起的部分），
  R0 即刻开工；PLAN.md 的 Phase 0/1 产出物（对照清单、schema 设计、SKU 标准）全部复用为 R0 输入。
