# 产品需求文档 PRD v1 — 新一代 Walmart Dropshipping ERP

- 日期：2026-07-09 · 阶段：R0 收尾 · 作者：PM+AR 帽 · 状态：**待 Owner 验收**
- 依据：业务规则总账 v1.2（21 域 187 规则）+ 决策日志（D-Q1~D-Q41）+ 数据调研 SYNTHESIS
- 定位：这是"要造什么"的定义。领域模型/数据字典列级设计、页面线框在 R0 后续 spec 展开；本文冻结范围、边界、架构骨架、迭代切分。

---

## 1. 产品愿景与一句话定义

**一个多团队协作的跨境电商 ERP，把「选品采集 → 合规审核 → 货源匹配 → 上架 → 在架维护 → 订单履约 → 售后 → 财务复盘」全链路收进一个系统，数据单源、平台可扩展、自动化程度可按团队调档。**

首发渠道 Walmart US + 采集源 Amazon；架构从第一天为多渠道/多采集源预留。

## 2. 目标与非目标

### 2.1 本产品要达成（对应决策）
- 取代当前 13+ 零散工具 + 飞书当库 + 多个本地 PG 的割裂现状，收敛为单一系统（D-Q6/Q7/Q12）。
- 支撑 12 个月内 **200 店 / 日上架 20 万 / 在线 200 万 SKU / 库内 500 万 SKU**（D-Q15）。
- 20-30 人多团队协作，功能级 RBAC + 团队数据隔离 + 全量操作审计（D-Q16）。
- 稳定性优先于进度，无硬性上线期限（D-Q37）。

### 2.2 明确非目标（MVP 不做）
- 促销/PROMO（D-Q1）、WFS 履约、手机端、老板看板（D-Q37）、自建邮件服务器（D-Q22 是客户端聚合）。
- 历史在线产品/订单的 ETL 迁移——ERP 建好直接从 Walmart 重拉（D-Q35）。

## 3. 用户与角色（RBAC 模型）

| 用户类 | 说明 | 典型角色（功能级权限，团队作用域内） |
|---|---|---|
| 超级管理员（Owner） | 唯一 | 全局；**独占**：建团队、跨团队资源共享开关、平台级配置 |
| 内部成员 | 20-30 人，属某团队 | 采集员（分不同采集功能权限）/ 审核员 / 上架员 / 维护员 / 订单员 / 财务 / 团队管理员（只读+配置） |
| 采购方 | 外部受限账号 | **采购方门户**：仅见分配给自己的采购执行单，处理+回填物流（D-Q27） |

- 团队隔离（D-Q30）：店铺**团队独占**；产品库/GTIN 池/合规黑名单**默认团队隔离**，超管可设共享。
- 审计日志（D-Q16）：所有写操作记录 who/when/what/team，永久留存。

## 4. 领域模型（限界上下文 → 核心聚合）

```
┌─ identity ── 团队 team / 用户 user / 角色 role / 权限 permission / 审计 audit_log
├─ channel ─── 渠道 channel(walmart_us…) / 店铺 store(+档案+凭证加密+收款标签)
│              / 代理 proxy(资产+生命周期) / 配额 quota_config(上架/下架/维护 三向)
├─ catalog ─── 产品主数据 product(master_sku 渠道中立 + source_channel/source_ref)
│              / 变体组 variant_group / 品牌占用 brand_assignment
│              / GTIN 池 gtin_pool(UPC-A 12 + EAN-13 13, 团队隔离, 水位告警)
│              / 类目映射 category_map(A叶子→WPT + 5维风险) / 货源 product_source(占位, 待1688 API)
├─ compliance ─ 黑名单品牌/卖家/ASIN/类目 / TRO案件 / USPTO商标 / 封店案例库
│              / 合规规则 rule / 命中记录 hit(软标记+团队级自动拦截开关)
├─ audit ────── 审核运行 audit_run(L0-L4) / 命中 audit_hit / LLM缓存 / 用量 usage_log
├─ listing ──── 刊登 listing(offer_mode: build|match) / feed / feed_item / listing_spec
│              / 生命周期状态机 / 错误分类 listing_error / 维护任务
├─ pricing ──── 定价策略注册表 pricing_strategy(按 offer_mode×团队×店铺)
├─ sourcing ─── 货源发现(占位) / 采购执行单 procurement_order(渠道单→分配采购方→采购→物流)
├─ order ────── 渠道订单 channel_order / 四检审核 / 采购方 purchaser / 履约
├─ aftersale ── 退货 channel_return / RMA / 退款(记录→审批→自动 三档)
├─ finance ──── 结算对账 settlement / 利润核算(SKU/店铺/团队 三粒度)
├─ scraping ─── 采集 server + worker 池(AIMD) / 采集任务 / 原始数据
├─ mail ─────── 店铺邮箱(IMAP/SMTP) / 邮件 / 封店邮件识别 → store_incident
├─ automation ─ 三档自动化策略引擎(人工/半自动/全自动, 各流程可切换) / 调度 / task_run
└─ notify ───── 站内通知中心(替代飞书+邮件)
```

**内部 SKU 标准（D1）**：`master_sku = M{7位自增}` 渠道中立终身不变；新上架 channel_sku=master_sku；存量 SKU=ASIN 只映射不迁移。

## 5. 核心业务流程（端到端）

### 5.1 建品上架主流程（offer_mode=build）
```
采集(Amazon) → 审核 L0-L4(walmart-audit-system 移植) → audit_passed
  → 货源匹配(sourcing, 有货源才继续) → 分配店铺+GTIN → 定价(build策略)
  → 变体分组 → spec 构建(零认证覆盖) → feed 提交 → 轮询 → 状态机回写 → 在架
  ↑ 审核→上架衔接: 三档(人工逐批/半自动/全自动) 可切换 [D-Q13]
```

### 5.2 跟卖上架（offer_mode=match）
```
选品采集(walmart-scraper: 产品ID/关键词/卖家) → 人工筛(未来自动选品筛选器)
  → 货源匹配(1688) → SPEC 可跟卖预检 → 分配店铺 → 定价(match策略, 现行人工指定)
  → MP_ITEM_MATCH feed → 轮询 PROCESSED → 推库存(默认5) → 在架
共用: 配额/提交轮询/生命周期/维护机器 [D-Q3]
```

### 5.3 订单履约
```
Walmart 拉单(15min) → 四检(钓鱼/采购方/限价/一致性, 软标记) → 分配采购方
  → 采购方门户领单 → 采购执行 → 回填物流(未来第三方物流 API) → ship 回传 Walmart
```

### 5.4 封店工作流（D-Q33）
```
邮件识别封店 OR 人工标记 → 记录封店时间+原因 → 释放该店全部 SKU+品牌占用
  → 定时提醒团队(观察放款/写申诉信) → [封店案例库 walmart_suspension_history 75k 辅助]
```

## 6. 关键非功能需求（NFR，容量设计唯一基准）

| 维度 | 指标 | 设计推论 |
|---|---|---|
| 规模 | 200 店/日 20 万上架/在线 200 万/库内 500 万 SKU | PG 核心表按 team+时间分区；listing/order/audit_run 分区表；无 SQLite 进生产 |
| 采集吞吐 | 日采 20 万+ ASIN | scraper server/worker 池水平扩展（AIMD），独立于 API/队列进程 |
| LLM 成本 | 20 万/日审核+映射 | flash 优先 + sha256 缓存 + L4 默认关；usage_log 团队级预算监控；粗估成本模型见 §9 |
| 可用性 | 稳定优先 | 每增量影子验证/A152 实测才算完成；DB 与应用分离部署 |
| 隔离 | 多团队 | 行级 team_id + RLS 或强制查询过滤；共享资源超管授权 |
| 审计 | 全写操作 | audit_log 不可篡改、永久 |
| 安全 | 凭证 | 加密存储(pgcrypto/Fernet) + UI 管理；采购方门户最小权限 |

## 8. 迭代切分（R1 行走骨架 → R2 领域纵深）

### R1 行走骨架（地基 + 一条最小闭环，全环节真实接线）
- **地基**（第一天就位，不可后补）：多租户+RBAC+审计日志、认证、CI、migration、结构化日志、通知中心骨架、DB 分区策略、docker-compose(pg+redis)。
- **最小闭环**：A152 单店 + 单 ASIN，采集→审核(L0-L3)→上架(dry-run/真上架)→轮询→状态回写→前端可见，含失败路径与错误处置。
- 验收：A152 现场演示全链路（含制造失败看告警）。

### R2 领域纵深（两周一迭代，每个模块影子对拍/A152 实测通过才算完成）
建议顺序（低风险只读 → 高风险写操作）：
1. 店铺档案+代理+配额中心+GTIN 池（含 EAN-13 导入、水位告警）
2. 合规数据标准导入接口（黑名单/TRO/USPTO/类目映射入库）+ 审核 L4 接入
3. 上架生命周期完整态机（build 模式 + UPC 闭环 + 变体组 + 错误分类处置）
4. 定价策略注册表 + 维护（价/库存/标题）
5. 跟卖模式（match offer_mode + 货源占位）
6. 订单四检 + 采购方门户
7. 售后 returns + 封店工作流 + 邮箱模块
8. 财务对账/利润核算 + 日报/KPI（analytics）
9. 三档自动化策略引擎全流程贯通
- MVP 完成判据：上述 1-9 在 A152 + 一个试点团队跑通闭环。

### R3+ 扩展（MVP 后）
店铺前台可售探针、跟卖自动选品、1688 API 货源发现、第二渠道/采集源 adapter、多平台。

## 9. LLM 成本模型（占位，R0 后精算）
- 审核：flash 为主，命中缓存 0 成本；4326 ASIN 已验证可行 → 按 usage_log 实测单价 × 20 万/日外推，团队级预算闸。
- 映射：类目映射多为静态查表（category_map 命中即 0 LLM），仅未命中走 embedding+LLM 复排。
- 结论：20 万/日的成本主要压在审核 L3，flash+缓存+L4默认关是既定控制手段；精确数字待 R1 用 A152 实测标定。

## 10. 待 Owner 验收的开放点

3. 云服务器选型与预算档位（决定采集池起步规模）。
